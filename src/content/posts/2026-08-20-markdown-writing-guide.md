Markdown 是一种轻量级标记语言。它不依赖复杂的排版软件，只需要一个普通文本编辑器，就可以写出结构清晰、方便版本管理的技术文章。

对于个人技术博客来说，Markdown 的优势主要有三个：

- 内容和页面样式分离，换主题时不用重写文章。
- 文件可以直接放进 GitHub，用 Commit 记录每次修改。
- 天然适合代码、命令、列表、表格和技术笔记。

## 一、文件命名规则

建议使用“日期 + 英文短标题”的方式命名文件：

~~~text
2026-08-20-markdown-writing-guide.md
2026-08-21-react-hooks-notes.md
2026-08-22-tcp-congestion-control.md
~~~

文件名建议遵循以下规则：

1. 使用小写英文、数字和连字符。
2. 不要使用空格、中文标点或特殊符号。
3. 文件名要能表达文章主题。
4. 文件扩展名必须是 `.md`。

文件名主要方便管理，文章真正的 URL 由 Front Matter 中的 `slug` 决定。

## 二、Front Matter 编写规则

Front Matter 位于 Markdown 文件最顶部，由两行 `---` 包围：

~~~yaml
---
slug: markdown-writing-guide
date: 2026.08.20
category: 工程实践
tags:
  - Markdown
  - 内容管理
title: Markdown 文件编写规则
excerpt: 文章摘要会显示在首页和文章列表中。
image: /assets/card-violet.png
readingTime: 10
draft: false
---
~~~

当前博客支持这些字段：

| 字段 | 是否必填 | 作用 |
| --- | --- | --- |
| `slug` | 是 | 生成文章 URL，例如 `/articles/markdown-writing-guide` |
| `date` | 是 | 文章日期，同时决定排序和归档位置 |
| `category` | 是 | 文章所属分类 |
| `tags` | 否 | 用于标签筛选和搜索 |
| `title` | 是 | 文章标题 |
| `excerpt` | 是 | 首页和文章列表中的摘要 |
| `image` | 否 | 文章封面图片 |
| `readingTime` | 否 | 预计阅读时间，单位为分钟 |
| `draft` | 否 | `true` 时暂时不显示 |

注意事项：

- 字段名必须拼写正确，大小写也要保持一致。
- `tags` 是数组，每一项前面需要有两个空格和一个短横线。
- `draft` 只能写 `true` 或 `false`。
- `date` 建议使用 `YYYY.MM.DD` 格式。
- `image` 必须从 `/assets/` 开始，不要写 `public/assets/`。

## 三、标题层级

一篇文章只使用一个一级标题。当前博客的文章标题由页面自动生成，因此正文建议从二级标题开始：

~~~md
## 第一个章节

### 第一个章节中的小节

## 第二个章节
~~~

不要为了放大文字而跳过层级，例如直接从 `##` 跳到 `####`。清晰的标题层级有助于生成文章目录，也方便读者快速浏览。

## 四、段落和强调

普通文字直接写成段落。不同段落之间需要空一行：

~~~md
这是第一段，介绍文章的背景。

这是第二段，开始解释具体实现。
~~~

常用强调方式：

~~~md
**重点内容**
*需要强调的词语*
`变量名或命令`
~~~

建议少量使用加粗和斜体。技术文章的重点应该通过结构和论证体现，而不是让整篇文章充满强调格式。

## 五、列表、引用和表格

无序列表使用短横线，有顺序的步骤使用数字：

~~~md
- 准备实验环境
- 编写最小示例
- 记录运行结果

1. 安装依赖。
2. 启动开发服务器。
3. 打开浏览器检查结果。
~~~

引用适合放置定义、结论或参考资料：

~~~md
> 先让问题可以被复现，再讨论如何优化。
~~~

表格适合整理对比信息：

~~~md
| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| Markdown | 简单、可版本管理 | 需要构建 |
| 数据库 | 查询灵活 | 需要维护服务 |
~~~

## 六、代码块规则

技术文章中的代码必须使用 fenced code block，并标注语言：

~~~md
~~~ts
const message: string = "Hello Markdown";
console.log(message);
~~~
~~~

当前博客会根据语言名称启用代码高亮，并提供复制按钮。常见语言名称包括 `js`、`ts`、`tsx`、`python`、`java`、`cpp`、`bash`、`json` 和 `yaml`。

代码示例应该尽量短小。如果一段代码超过一个屏幕，建议拆成多个步骤，并解释每段代码解决什么问题。

## 七、图片和链接

图片放在 `public/assets/` 目录中，文章里使用 `/assets/` 路径：

~~~md
![Markdown 文件结构示意图](/assets/markdown-structure.png)
~~~

图片说明文字应该描述图片内容，而不是简单写“图片”或“截图”。

外部链接使用以下格式：

~~~md
[React 官方文档](https://react.dev/)
~~~

如果链接指向代码仓库、官方文档或论文，建议在文字中说明来源，方便读者判断链接价值。

## 八、技术文章推荐结构

一篇完整的 CS 技术文章可以按照下面的顺序组织：

1. 问题背景：为什么要研究这个问题？
2. 基本概念：读者需要先了解什么？
3. 实现过程：具体做了哪些步骤？
4. 代码示例：最小可运行示例是什么？
5. 实验结果：运行结果和预期是否一致？
6. 问题复盘：遇到了什么错误，如何解决？
7. 总结：这次实践留下了什么结论？
8. 参考资料：使用了哪些文档、论文或仓库？

不要只记录“我做了什么”，还要解释“为什么这样做”和“还有哪些替代方案”。这会让文章从操作记录变成真正可复用的技术资料。

## 九、发布前检查清单

提交文章前，可以快速检查：

- 文件名是否符合命名规则？
- `slug` 是否唯一？
- 标题、日期、分类和摘要是否填写？
- `tags` 是否使用正确的 YAML 数组格式？
- 图片路径是否从 `/assets/` 开始？
- 代码块是否标注语言？
- 标题层级是否从 `##` 开始？
- 链接和图片是否能正常打开？
- 是否需要暂时设置 `draft: true`？
- 本地运行 `npm run build` 是否通过？

## 总结

Markdown 的核心不是记住所有符号，而是建立稳定的内容结构：Front Matter 管理元数据，正文负责解释问题，代码块展示实现，标题和列表帮助读者导航。

在这个博客中，写作流程可以保持为：

~~~text
新建 .md 文件
→ 填写 Front Matter
→ 编写 Markdown 正文
→ 本地预览和构建
→ 提交到 GitHub
~~~

只要遵循统一规则，文章数量增加后仍然可以保持易读、易搜索和易维护。
